# Project Specification: Cross-Architecture GPU Translation Layer (LLVM-Based)

**Project Name:** `CUDA_Translator`  
**Version:** 1.0-RFC  
**Target Architectures:** AMD ROCm (RDNA / CDNA), Universal Vulkan Compute (SPIR-V), Google Cloud TPU (Pallas / Mosaic via XLA)  
**Source Ecosystem:** NVIDIA CUDA (PTX Virtual ISA / CUDA Driver API)

---

## 1. Executive Summary & Objective
The objective of this project is to build a high-performance, hardware-agnostic translation layer that enables applications optimized for proprietary NVIDIA CUDA ecosystems to run natively on alternative hardware architectures (specifically AMD ROCm and universal Vulkan Compute).

Unlike source-to-source regex converters (e.g., standard text-replacement HIPIFY scripts), this project operates at the **compiler and runtime intermediate representation (IR) level**. By ingesting compiled intermediate code (PTX / NVPTX LLVM IR) or intercepting Driver API runtime calls, the translator decouples high-level mathematical kernels from proprietary microarchitectures, performing automated hardware normalization passes to preserve hardware utilization.

---

## 2. Hardware Microarchitectural Differences & Mapping Challenges

| Dimension | NVIDIA SM (e.g., Ampere / Ada / Hopper) | AMD CU/WGP (RDNA 3 / CDNA 3) | Vulkan Compute / SPIR-V |
| :--- | :--- | :--- | :--- |
| **Execution Granularity** | **Warp: 32 threads** | **Wavefront: 32 (RDNA) or 64 (CDNA/GCN)** | **Subgroup: Vendor-dependent** (16, 32, 64) |
| **Active Thread Masking** | 32-bit `activemask` (`__ballot_sync`, `vote`) | 64-bit `EXEC` register (CDNA) or 32-bit (RDNA) | `subgroupBallot` (`uvec4`, 128-bit) |
| **Shared Memory / LDS** | 32 banks, 4 bytes/bank (128 bytes/stride) | 32 or 64 banks, 4 bytes/bank | Shared Memory (`Workgroup` storage class) |
| **Intra-Warp Communication** | `shfl.sync.bfly`, `shfl.sync.down` | `ds_bpermute`, `ds_swizzle` | `subgroupShuffle`, `subgroupShuffleXor` |
| **Matrix Tensor Cores** | WMMA / MMA (e.g. 16x16x16 FP16/FP32) | MFMA (CDNA) / WMMA (RDNA 3) | `VK_KHR_cooperative_matrix` |
| **Driver Interface** | `nvcuda.dll` / `libcuda.so` (`cu*` API) | `hiprtc` / `libamdhip64.so` | Vulkan ICD (`vulkan-1.dll`, `libvulkan.so`) |

## 3. Core Architectural Requirements

### A. Intermediate Representation (IR) Strategy
1. **Neutral GPU IR (Cross-Arch IR)**:
   - A hardware-neutral, static single assignment (SSA) representation modeling GPU compute pipelines.
   - Preserves thread-hierarchy semantics:
     $$\text{GlobalID}_d = \text{GroupID}_d \times \text{BlockDim}_d + \text{LocalID}_d$$
   - Abstract memory address spaces: `Global`, `Shared` (LDS), `Local` (Private Stack), `Constant`, `Param`.
2. **Frontend Ingestion**:
   - Ingests **PTX virtual assembly** generated by `nvcc` or `clang -target nvptx64-nvidia-cuda`.
   - Ingests or intercepts **CUDA Driver API calls** (`cuLaunchKernel`, `cuMemAlloc`, `cuMemcpyHtoD`, `cuModuleLoadDataEx`).
3. **Backend Lowering**:
   - Lowering to **Vulkan SPIR-V / GLSL Compute Shaders** for universal deployment across AMD, Intel, and Apple GPUs.
   - Lowering to **AMD ROCm / HIP C++ / AMDGPU LLVM IR** for dedicated high-performance datacenter accelerators.

---

### B. Automated Mapping & Hardware Abstractors

#### 1. Warp (32) to Wavefront (64) Scheduling Translation
When running 32-thread warp logic on 64-thread wavefront hardware (e.g. AMD CDNA MI200/MI300 or GCN):

* **Strategy 1: Masked Half-Wavefront Execution (Correctness-First)**:
  - Allocate a 64-thread wavefront but dynamically mask the upper 32 threads using an execution predicate:
    $$\text{Active}(t) = [0 \le t < 32]$$
  - Active threads execute normally; upper threads are disabled (`EXEC[32..63] = 0`).
  - Guarantees 100% semantic identity with zero thread divergence penalty between distinct warps.

* **Strategy 2: Dual-Warp Coalescing (Throughput-Optimized)**:
  - Fuses two adjacent 32-thread warps ($W_{2k}$ and $W_{2k+1}$) into a single 64-thread wavefront:
    $$\text{WarpID} = \lfloor t / 32 \rfloor, \quad \text{LaneID} = t \pmod{32}$$
  - **Ballot Mask Transformation**:
    $$\text{Ballot}_{64} = (\text{Ballot}_{W_{2k+1}} \ll 32) \lor \text{Ballot}_{W_{2k}}$$
  - **Shuffle Remapping**: Intra-warp shuffles (`shfl.sync.bfly`, `shfl.sync.down`) are clamped to 32-lane sub-boundaries to prevent invalid cross-warp register snooping.

#### 2. Virtual Memory & Shared Memory (LDS) Bank Normalization
* **Bank Conflict Resolution**:
  - NVIDIA SMs use 32 banks with 4-byte boundaries. Bank index is computed as:
    $$\text{Bank}_{\text{NVIDIA}} = \left(\frac{\text{Address}}{4}\right) \pmod{32}$$
  - AMD LDS architectures can feature 32 or 64 banks with differing stride interleave patterns.
  - The compiler analyzes LDS access strides and automatically injects padding bytes into workgroup shared memory declarations:
    $$\text{AllocSize}_{\text{padded}} = \text{AllocSize} + \lfloor \text{Rows} \times \text{Padding} \rfloor$$
  - Prevents serialization where multiple lanes within a wave simultaneously address distinct offsets within the same bank.

#### 3. Matrix Acceleration Routing (Tensor Cores $\to$ Matrix Units)
* **Detection**: Identifies PTX matrix multiply-and-accumulate instructions:
  `wmma.load.a.sync`, `wmma.load.b.sync`, `wmma.mma.sync.aligned.m16n16k16.f32.f16`
* **Translation Targets**:
  - **AMD CDNA MFMA**: Maps 16x16x16 FP16 matrix operations to `v_mfma_f32_16x16x16f16`.
  - **Universal Vulkan**: Maps to `VK_KHR_cooperative_matrix` (`OpCooperativeMatrixMulAddKHR`), allowing vendor drivers (AMD, Intel, NVIDIA) to bind native matrix hardware.

## 5. Architectural Guarantees & Constraints
1. **Zero Double-Buffering Overhead**: Kernel argument bridging and device pointer translation operate with zero-copy where unified memory or host-visible buffers are supported.
2. **Deterministic Synchronization**: Barrier semantics (`bar.sync`) strictly map to target workgroup memory barriers (`workgroupBarrier()` / `__syncthreads()`) with memory fences.
3. **Open Standards First**: Built with open APIs (Vulkan Compute, SPIR-V, HIP, LLVM IR, OpenXLA) without reliance on proprietary non-distributable toolchains.
